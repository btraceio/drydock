# Decision contract: Project SDLC workflow selection and local invocation slice

meta: author-model=ChatGPT, date=2026-11-18, inputs=Requirements-5UJyXN2P.md (including recovered amendments); WorkflowBrief-5UJyXN2P.md; repository AGENTS.md; source evidence and cairn citations below

## Goal and non-goals

Settle the IntelliJ project's workflow schema, bounded registered-checkout resolution, immutable resource model, prompt composition, source/error UX, local launch/request integration, explicit PR/local intent and `review_scope` integration-instructions contract. This is a complete decision contract for this bounded slice, not the full feature contract or permission to implement it.

Remote workspace-box workflows and ordinary reviews remain required product scope. The next bounded contract implements the typed materialization/review-capability boundary below and designs transport, enrollment, remote scope/diff/source/backend/workbench delivery and remote cleanup. Those components are dependencies, not dropped requirements. Their mechanisms are not delegated to this slice's expander; full-feature implementation-plan approval remains blocked until the next contract settles and verifies its boundary obligations. This contract deliberately does not design SSH, a Python bridge or remote snapshot/backend internals. Numbers above INV-39 and AC-29 are reserved for that pass.

Binding non-goals: standalone parity; saved/planned task policy changes or a task namespace; global/parent/worktree overrides; YAML, expressions, shell hooks, automatic skill discovery/installation; project settings editor; general prompt editor or workflow-execution MCP command; changing Sphinx, review replies or automatic maintenance methodology; new remote providers/offers or fresh remote PR cloning/provisioning. Planning does not authorize source/test/build changes, builds/tests, provisioning, commits or subagents.

### Schema and applicable selection

Introduce headless `app.drydock.sdlc` types and focused parser/resolver/composer helpers under `src/main/java`; platform controllers consume them. Configuration remains a hand-edited `.sdlc/config.json`, with mandatory integer `version: 1` and only these optional paths:

| Invocation | Configuration leaf |
| --- | --- |
| Free-form prose New task | `newTask.prePrompt` |
| GitHub or Jira Implement | `actions.issue.implement` |
| GitHub or Jira Triage | `actions.issue.triage` |
| Explicit ordinary PR review | `actions.pullRequest.review` |
| Explicit ordinary local review | `actions.localChanges.review` |

Each present selected leaf is an object containing exactly one nonblank string `skill`, `file` or `text`, plus optional `include` array of nonblank relative-path strings. Empty include is valid. `skill` names a file whose final name is `SKILL.md`, not an installed skill name or a directory. Its bytes/frontmatter are followed as project instructions; no harness-specific metadata execution, name discovery or frontmatter feature emulation. `file` is plain prompt text. `text` is literal inline methodology and may also declare includes.

Add a proposed strict `JsonParser.parseStrict(String, int maxDepth)` entry point reusing the JSON value model, rejecting duplicate members, non-RFC whitespace/number syntax and invalid Unicode scalar sequences. Existing `parse(String)` semantics remain unchanged. The workflow decoder checks root/version/namespace objects and unknown keys in those containers. It validates only the applicable leaf's definition and resources; invalid unrelated leaves do not prevent a valid selected leaf. Unknown fields inside a selected definition, null selected leaves/containers, wrong types, multiple sources and blank definitions are invalid. An omitted container/leaf is missing, not an error. A missing config means proven absence of the config entry; unreadable config, a dangling config symlink or failed existence probe is Invalid, never Missing. Unknown generic `actions.implement/triage/review` keys are errors, not aliases.

Malformed JSON, unsupported/missing version or malformed namespace structure invalidates any invocation that consumes configuration. A malformed unselected definition body does not. Blank/native-command free-form input, Save for later, saved/planned tasks and excluded actions bypass the resolver entirely, including config existence/validation. PR/local absence falls back independently; neither inherits the other or issue/free-form policy.

### Root, bounds and immutable bundle

A proposed `ProjectWorkflowResolver.resolve(SharedProject, WorkflowTarget, Cancellation)` is blocking and headless; a platform controller supplies an actual registered project obtained through `plugin.sharedProjects().byRoot(...)`/registered repository ID. Canonicalize the registered root off EDT, then resolve only that root's `.sdlc/config.json`. Never search the session worktree, PR checkout, remote checkout, parents, user-global settings or installed skills.

For an unregistered New task, retain the existing register-first operation on the accepted Start attempt, before consuming config, while retaining the dialog and its edits. Do not register just to preview/open/cancel a dialog. Show “Project not registered; workflow resolves on Start” until that operation finishes. If no existing register-first path applies, unresolved registered identity is a visible selection failure with default-once/cancel, never permission to use a synthetic SharedProject ID or guess a checkout. Existing-session review resolves by the session's registered repository identity, not the hosting window's project.

Choose these concrete fixed ceilings, with exact-limit success and limit-plus-one failure tests:

| Resource | Limit |
| --- | --- |
| Configuration bytes / JSON container depth | 256 KiB / 32 |
| Selected prompt UTF-8 bytes (text/file/SKILL.md) | 128 KiB |
| Explicit include roots | 64 |
| Bundle entries, including directories and links | 2,048 |
| Supporting regular file / aggregate regular-file bytes | 8 MiB / 32 MiB |
| Resource traversal or link-chain depth | 32 |
| Normalized repository-relative path UTF-8 length | 1,024 bytes |
| Resolution/snapshot preparation deadline | 15 seconds, cancellable and generation-fenced |
| Retained bundles per managed session / session bytes | 16 / 256 MiB |
| Aggregate plugin-owned retained workflow bytes | 1 GiB |

Counts and byte totals are enforced during enumeration and bounded reads, not merely by `Files.size`; deduplicate overlapping entries by normalized destination and reject conflicting bytes/types. Resource limits include actual symlink targets included in the bundle. Deadline/cancellation settles the invocation without launch; a tardy filesystem completion only releases its pending resources. Do not pretend Java can forcibly interrupt every OS filesystem stall.

Paths are repository-relative literals: reject absolute/drive/UNC/URL paths, NUL/control characters, expansion syntax and normalized escapes; never expand tilde/environment variables. A prompt file or SKILL.md must be a readable, nonblank strict UTF-8 regular file. Supporting resources may be binary and retain executable bits. Reject devices, sockets, FIFOs, broken/cyclic links, repository-root directory selection and `.git` administrative entries. No automatic dependency discovery or repository-wide fallback copy.

Check both lexical and real-path containment, including `.sdlc/config.json`, source, every include and each walked entry. Read through a pinned canonical-root directory handle with descriptor-relative no-follow traversal (`SecureDirectoryStream`); resolve symlink chains within that pinned tree rather than opening unchecked string paths. If the filesystem cannot provide safe traversal, fail visibly instead of weakening containment. Check attributes/entry set before and after capture; detected concurrent replacement/change is a retryable visible resolution error, not missing or a mixed-content success.

Preserve the selected source's logical repository-relative layout. A skill selects its complete containing directory; a file selects itself; text selects no implicit files; all add declared includes recursively. Preserve contained symlinks as links, rewriting absolute contained targets to bundle-relative links. A link's destination must also be in the selected set (or be an ancestor directory containing selected descendants); require an explicit include for an otherwise unselected destination. Do not recursively copy undeclared targets to make broken references work. Preserve necessary link/ancestor entries along the selected path as well as selected resolved descendants, so a symlink in a source/include parent does not silently change its resource base. No link in the resulting bundle may point outside staging. Other relative dependencies outside the skill directory require explicit includes; static discovery is not promised.

Capture selected prompt bytes, supporting entries, hashes and executable/link metadata into one immutable `SelectedWorkflow`/`WorkflowBundle` before acceptance. No later file or harness change re-reads that selection. This is an invocation snapshot, not a claim of transactional filesystem snapshots across unrelated concurrent edits. A new invocation resolves afresh; a user explicitly retrying a failed preparation starts a new generation. Do not poll/watch/reconfigure running actions.

Materialize selected bundles into private plugin-owned, per-session staging with a separate generated instruction file, preserving the repository-relative tree. Never overwrite checkout workflows or register/install a native/global skill. Published snapshot files are read-only to normal consumers, with executable source files remaining executable; configuration loading never executes scripts. A prompt supplies the exact materialized source location and resource base. Project skills remain ordinary instructions; scripts run only if the agent's existing mode/permissions allow them.

A pending invocation owns staging until accepted launch/delivery; on success its lease transfers to an application-owned session resource owner. Keep every delivered bundle for the retained conversation, including idle/resumable states, so later prompts/resume do not find deleted paths. Cancellation, known no-send and failed launch release pending resources; ambiguous delivery retains resources because the agent may have consumed the reference. Do not delete an earlier delivered bundle on the next invocation. Session deletion releases its namespace; application shutdown flushes lease manifests without destroying retained conversation resources. Startup recovers owned manifests, removes abandoned pending/orphaned namespaces and reports cleanup errors. Cap exhaustion fails visibly, never evicts resources still referenced by a retained conversation. This resource manifest is not a second writer of ApplicationState.

### Composition and model policy

Use a pure proposed `WorkflowPromptComposer`; keep policy selection independent from integration/target context. Represent invocation origin explicitly, rather than recognizing seed strings. NewTaskPreset gets an explicit workflow applicability descriptor; segmentStart and conflict-resolution presets are excluded, while empty/mainCheckout/start free-form presets are eligible. PR-associated free-form New task is still free-form, not a PR review.

For unconfigured actions preserve current prompt output/default methodology, title guidance, modes and existing model-role behavior. For configured free-form prose replace CLARIFY_FIRST only with the resolved prePrompt; retain title guidance and `CreateContext.TASK_SEPARATOR` exactly, with the user's task unchanged after it. Do not seed the task editor with the prePrompt. Blank input sends no initial prompt; a single-line native command recognized by `isSlashOneLiner` is sent byte-for-byte with no framing, title, tier rule or separator. Show “Pre-prompt not applied: harness command” or “Pre-prompt not applied: blank chat”. No bundle or config is consumed for these cases. Prose transitions invalidate bypass and resolve normally; no provider-specific expansion or two-message orchestration.

Configured issue actions replace WORKFLOW_STEPS/TRIAGE_STEPS, QUALITY_GATES, definition-of-done, clarify-first and built-in role/delegation assignments. Retain immutable action identity (Implement/Triage, GitHub number/title/URL or Jira key/summary/URL), session naming, existing fixed worktree/mode rules and title integration. The GitHub closing-keyword step and default PR completion/reproducer-approval strategy belong to the displaced built-in methodology, not mandatory UI integration. Preserve them only in the default path. Jira remains read-only as an integration; project prose does not expand its authority.

For configured issue prompts seed the existing instructions editor with the selected methodology content, preserving file/skill bytes as text. Keep target identity outside the editable methodology and add it once during final composition. The effective edited methodology is authoritative; materialized original source is supporting provenance, not an instruction to discard the edits and reload it. Supply the original skill/file resource base even when the method text was edited. Free-form task edits remain task text, not edits to the separate prePrompt. Do not add a general workflow editor for review actions.

Track generated seed, effective text, user-edited flag, selected snapshot, source provenance and input-generation separately. Only an unedited generated seed can be recomposed after a harness/source preparation change. A late result cannot overwrite current text. Fallback changes the selected source and only unedited generated text; edited text remains and the indicator says “Edited for this invocation; based on …”. A one-time default choice is attached to this applicable target and generation, not remembered globally or reused on a new invocation. Harness switches within a confirmed snapshot do not cause config re-reading or erase edits/model selections.

Project workflows own delegation strategy. Keep starting-model CLI choices and explicitly accepted tier values, including intentionally cleared choices, but remove built-in role-to-tier mapping and mandatory subagent dispatch. For project workflows expose tier values as a role-neutral conditional catalogue: if the workflow chooses a tier, that tier uses the user-selected exact model; unselected tiers resolve by existing starting-model rules. Do not invent mappings between project role names and tiers, or require delegation. On harnesses without subagents, do not emit tier rules. Existing remembered/model picker behavior remains, including the active-session reality: Run cannot change the model of an already-running agent by pretending a new-launch picker applied.

### Source/error UX and asynchronous ownership

Introduce a small platform invocation controller, separate from TaskLauncher/TaskTreePanel, with states preparing, ready, waiting-for-explicit-fallback, accepted, cancelled and committed. Each preparation has a generation/token and immutable UI input capture. Show “Resolving project workflow…”/disabled Start or visible progress immediately; a background executor handles registry/root/config/source/staging work. UI labels/dialogs only run on EDT. Move WorktreeReview's current `toRealPath` in its EDT entry into background preparation too.

NewTaskDialog and ReviewModelDialog show “Drydock default” or “Project <configuration leaf>: <skill/file relative path or inline text>”; indicate edited/default-once provenance. Quick Review and existing-session Run show the same source in their progress/result surface before dispatch, without adding a model/prompt editor. Never expose credentials, staging secrets or raw absolute remote connection details in indicators. Missing config/leaf selects labelled default. Invalid selection stops and offers exactly “Use Drydock default for this invocation” and “Cancel”, with a useful key/path/limit reason. No automatic correction, file rewrite or global setting.

The controller clears progress on success, failure, exception, timeout, refusal, cancellation and disposal. Validate generation, current target/input, project/controller liveness and cancellation before every EDT update, acceptance, materialization handoff, spawn or prompt commit. Close/cancel invalidates pending generations; late completions release resources but cannot reopen a dialog, alter edited text, spawn or submit. Once commit-to-send has occurred, cancellation cannot claim the prompt was not sent; show the actual/ambiguous outcome instead. Explicit fallback cannot bypass missing mandatory review capabilities or authorize a foreign scope.

### Explicit review intent, routing and once-only Run

Introduce a proposed `ReviewSelection` carrying registered repository ID, actual checkout/session reference, explicit target (`LocalChanges` or `PullRequest(PullRequestTarget)`), origin and requested `ReviewTour.Kind`. It is separate from ReviewScope and ManagedAgentSession.targetPullRequest association metadata. PR intent requires a valid explicitly selected PR identity from the PR action or deliberate workbench target selection. Incidental `pr-N` branch names, scope.pr metadata or session associations do not create intent. Invalid/stale explicit PR selection is a visible error, not silently relabelled local intent.

Carry it from PR row -> PullRequestReview -> ReviewTabOpener/workbench context -> workbench Run -> WorktreeReview start/existing-session request -> resolved authorized scope. Local tree Review/Quick Review and TaskActions.reviewChanges originate local intent unless the human explicitly selects a PR. Keep a lightweight workbench target context keyed to the live checkout/scope and generation, not inferred from cwd. Display that target and permit an explicit local/valid-PR selection in the existing review controls; missing context defaults to explicit local, never incidental PR inference. Revealing a session/Changes link does not itself invoke or adopt PR intent from its metadata.

The selected workflow follows this intent even when a PR review's existing worktree diff includes uncommitted changes. Preserve ReviewScopeRegistry identity, git base/head selection, diff contents, stable line keys/hunk IDs and annotation ownership. SessionReviewScopeResolver still resolves checkout scopes as before; add an exact-scope authorization/binding seam for an already-selected workbench scope rather than resolving a different scope merely to match policy. Foreign/running-owner conflict refuses; never rebind another live session to force a review.

Explicit workbench Run (sections/tour), including on an existing session, is a new invocation: resolve policy and presentation afresh, authorize the actual session/scope, check attached delivery and submit once via ReviewRequest/AgentExecutionRegistry. Do not launch a second agent when one already owns that checkout. This deliberately corrects today's silent join-only behavior even with no config and must be surfaced at plan approval. Pure focus/reveal/join is non-invoking. Idle-tree Quick Review's already-running race may remain focus-only, with “Focused existing session; no new review sent”; do not claim the newly selected workflow/model was run. Carry origin explicitly so this race cannot swallow a workbench Run.

New ordinary reviews keep the initial-prompt-before-spawn channel through SessionDialogs. A configured workflow's missing mandatory integration stops before agent execution; it cannot degrade to a naked methodology prompt. Preserve existing default-only launch complaint behavior where no new project policy is being consumed. Sphinx keeps its fixed/native command path, availability checks and running-session submission; it never consumes project review policy.

For configured in-session reviews, keep submitPrompt's single-line/control-character restrictions. Materialize a generated instruction file containing exact effective methodology, target/resource context, model constraints and the authorized integration lookup directive. Send only a short generated single-line directive to read that file and use the scope handle; quote generated references, not arbitrary source text. This preserves Markdown/script snippets without flattening or weakening terminal safety. Existing default requests may keep their existing single-line instruction form, with selected mode support added. No tmux sender, hidden console or automatic retry after ambiguous delivery. DELIVERED is reported as submitted, not proof of agent execution.

### review_scope include=instructions

Extract a proposed integration-only renderer from plugin ReviewInstructions, leaving existing `forScope`, `forSections`, Sphinx and maintenance callers behavior-compatible. Reuse shared output clauses to avoid divergent defaults. Project launches direct the agent to the selected workflow/resource base and to `review_scope(scopeId, include="instructions")`; the project skill itself needs no Drydock-specific clauses.

Add a separate ephemeral review-invocation binding, keyed by actual authorized `(ManagedSessionId, scopeId)`, carrying invocation generation, explicit target and selected ReviewTour.Kind. Install it immediately before fresh spawn/request commit, not during preview. Serialize concurrent user requests per session; known no-send can roll back only its own generation, ambiguous sends retain that generation. Remove bindings on scope revocation/session removal/backend close; rebinding never grants addressability. An earlier agent operation and a later human request are not promised simultaneous presentation modes on the same scope: the latest committed invocation is authoritative.

Add a proposed `McpSessionContext.reviewIntegration(scope, caller)` query. Router calls it only after existing live-session and scope authorization. Workspace context reads the invocation binding; absent a binding, use the existing stored tour kind from `tourOf(scope.id())`, otherwise TOUR. No JSON mode/target override parameter is introduced. This compatibility fallback supplies output form only, not workflow selection or new authority.

Opt-in response adds `instructions: {version: 1, mode: "tour"|"sections", text: <integration-only instructions>}` on the first page only. Without opt-in, existing fields/behavior remain unchanged. Accept `instructions` in the existing comma-separated include grammar and describe it in the existing tool descriptor. Bound the generated payload to 32 KiB; charge its serialized bytes against the same hunk budget as other extras. Return it whole, with `instructionsOverBudget: true` if it alone exceeds the caller's budget; never truncate or silently omit the required contract. Cursor pages do not repeat it.

The text names the authorized handle, reading review_state/prior decisions, current line keys/hunk IDs and digest distinction, finding anchors and unanchored whole-change findings, intent/takes/red-flag finding references, ordering/coverage and validation-repair protocol. TOUR requires educational checks/alternates, grounding/teaching/predict visibility and anchor/impact/diagram rules; SECTIONS explicitly uses kind sections and no checks. These are UI output-authoring requirements, not project review methodology. Include no code-review-subagent mandate, quality-gate workflow, project content/host paths, permission grant or model-role strategy. Existing validators, limits and authorization remain authoritative.

### Small typed local/remote integration boundary

Introduce the following headless value contracts in `app.drydock.sdlc`; names/signature shapes here are proposed APIs. No remote implementation is implied:

- `WorkflowTarget`: FREE_FORM_PRE_PROMPT, ISSUE_IMPLEMENT, ISSUE_TRIAGE, PULL_REQUEST_REVIEW, LOCAL_CHANGES_REVIEW. Excluded actions never manufacture a target.
- `WorkflowResolution`: sealed Missing(reason), Selected(SelectedWorkflow), Invalid(WorkflowProblem). Invalid retains config key/source and safe error category; it is never Optional.empty. UI cancellation/default-once are controller decisions, not resolver defaults.
- `SelectedWorkflow`: registered RepositoryId, target, SourceDescriptor(kind, configuration key, optional repository-relative source), exact prompt text, immutable WorkflowBundle and snapshot digest. No remote/local execution flags, secrets or mutable filesystem handles. Byte arrays have defensive-copy/value semantics.
- `WorkflowBundle`: normalized repository-relative entries (regular bytes/hash/executable, directories, contained relative symlinks), source/resource-base locations, selected include roots and measured counts/bytes. No host absolute path, task receipt, credential or arbitrary repository crawl. Empty bundles are valid for text without includes.
- `WorkflowMaterializationRequest`: invocation ID/generation, selected workflow, execution destination (LOCAL, LOCAL_EVAL, WORKSPACE_BOX), existing SessionMode and optional review context (explicit target, actual ManagedSessionId, scopeId, ReviewTour.Kind). The platform supplies verified session identity; this record is not authorization.
- `WorkflowMaterializer.materialize(request, cancellation)`: asynchronous success with MaterializedWorkflow, or typed failure; cancellation is a distinct result. It consumes captured bytes, never re-reads config/checkouts. Local implementation belongs to this slice; workspace-box implementation belongs to the next contract.
- `MaterializedWorkflow`: invocation/snapshot identity, destination-scoped resource/source/instruction-file references and a WorkflowResourceLease. References distinguish local Path from remote path text; a remote reference is never coerced into a host Path or LaunchResources. Composer uses only references matching the destination.
- `WorkflowResourceLease`: one cleanup owner at a time, idempotent release and explicit pending-invocation -> retained-session transfer; asynchronous cleanup/flush. Materialization retains responsibility for partial artifacts until success transfers the lease. Remote detach is not session death; the next pass implements the same retained-conversation ownership there.

Local adapters pass only selected staging context to providers. Keep it typed separately from task `LaunchResources.taskGuidance`/receipt resolution; local host adapters may union its staging root into extra read-context directories without replacing task resources. Introduce optional typed local-workflow resource access in CreateContext/ResumeContext and the SessionDialogs/DrydockSessionService handoff, defaulting absent for old call sites. Providers do not gain native skill-installation behavior. For Claude eval, add a narrowly typed read-only mount of the plugin-owned per-session workflow namespace via ClaudeEvalContainer.wrap; establish the empty namespace on new launch/resume so a later in-session invocation is visible without restarting the agent. Retain existing eval gates, task-host-resource refusal and container cleanup. Do not treat an unmounted host path as usable. An already-running process without usable resource access fails visibly rather than executing a guessed path; explicit default/cancel remains available for the workflow selection, not a license to bypass review tools.

The next contract implements WORKSPACE_BOX materialization plus a real remote review capability provider for existing remote sessions; local code must not hard-wire local `WorktreeService` or `Path` probes into that branch. It consumes this slice's frozen bundle/target/mode/context, returns destination-valid references and lease, and provides authorized actual remote scope/diff/source/output wiring for the same review-instructions contract. A boolean “remote MCP available” or local credential descriptor alone is not capability evidence. ReviewSelection and the capability query must distinguish ready, unavailable and unverifiable, attached delivery and enrollment; they do not provision or restart anything.

Inherited requirements for that implementation: existing Claude workspace-box offers/gates only; remote REVIEW_TOOLS_AND_RENAME and Spawn.FORBIDDEN with no direct task/spawn dispatch, TASK_INSTRUCTIONS or task guidance; no host LaunchResources/receipt transfer; registered-source isolated staging; bounded transfer/preflight; no auto-installation; application-owned MCP lifetime surviving console detach while IDE remains open; generation fencing/secrets/no mutation replay; manual existing Stop then Resume for proven legacy non-enrollment, same nonempty agentSessionId, no replacement conversation or retained review request; inaccessible/malformed evidence is not proven absence. An enrolled detached agent keeps tools/data but new human Run requires Resume/reattach and explicit retry, never queuing/replaying a prompt. The approved ProcessRunner tunnel-lifetime exception and its narrow AGENTS amendment are next-pass concerns, not permission to create ad hoc ProcessBuilder infrastructure here.

## Rejected alternatives

- REJ-1: Session/worktree/remote/parent/global lookup or sharing UserConfig's lenient decoder — rejected because registered project content is the only authority and invalid is not missing.
- REJ-2: Appending project text to built-in clarify-first/quality-gate/delegation methodology — rejected because project strategy must replace, not contradict, the default strategy.
- REJ-3: PR policy inferred from scope.kind, pr-N branch or session association — rejected because explicit PR intent may legitimately retain a worktree diff, and local reviews may have incidental PR metadata.
- REJ-4: Replacing diff identity/content to make target routing easier — rejected because it can lose uncommitted changes and strand findings/line-key consumers.
- REJ-5: Loading/staging prePrompt for native commands, blank chat or Save for later — rejected because unused invalid policy must not block these non-consuming paths or turn chat into a task.
- REJ-6: Native harness skill registration, frontmatter feature emulation or script/dependency execution during resolution — rejected because the contract is project instruction/resource delivery, not executable config or installation.
- REJ-7: Re-resolving files after acceptance, overwriting edits on completion, or process-exit-only cleanup — rejected because source snapshots/edits must survive and idle resumable conversations still reference resources.
- REJ-8: Sending multiline project Markdown through submitPrompt, flattening it, or adding another/tmux sender — rejected because the existing terminal safety contract forbids it and flattening changes instructions.
- REJ-9: Treating explicit Run as focus-only, auto-retrying PTY writes or queuing detached-agent requests — rejected because Run must invoke once while ambiguous delivery cannot safely be replayed.
- REJ-10: Reusing task LaunchResources as the remote workflow payload or assuming a tunnel proves remote review works — rejected because host paths/task authority are incompatible and actual scope/diff/source/output integration is required.
