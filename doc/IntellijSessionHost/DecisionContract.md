# Decision contract: One reusable IntelliJ Sessions editor retaining independent consoles

## Goal and non-goals


Replace per-session live editor documents by one reusable **Drydock Sessions** editor per owning IntelliJ project, retaining up to twenty independent sessions and an explicitly held different-session secondary pane inside that document. Reduce editor clutter without replacing terminal/process ownership. Preserve explicit Enter/double-click Start-or-Resume for stopped navigator rows, and supply discoverable all-session access and an in-memory previous-session return action.

Authority is deliberately separated:
- Operator-selected, relayed in spec R1–R7: editor-area location, default production replacement (not a flag/prototype/dual mode), independent retained consoles, stopped-row explicit launch semantics, exactly one held different-session secondary per project, A/B previous action without persistent MRU or default shortcut, and unchanged worktree/project/process/bridge boundaries.
- Coordinator-selected architecture in this stage, **subject to final operator contract/plan approval**: one internal two-pane split; Hold moves the current primary into an empty secondary and leaves primary empty; occupied secondary must be explicitly closed before another Hold; hold survives presentation hide/reopen in-process but not restart; unfiltered All Sessions picker; canonical address with migration-only old UUID placeholders; conservative first-upgrade no-selection fallback described below.
- Spec A1–A9 remain **nonblocking FINAL-APPROVAL assumptions**, not retrospectively operator-selected requirements. Their edge behavior is explicit under ASM-1–ASM-6. Implementation approval remains a blocker even after contract/plan gates pass.

Non-goals are binding: no tool-window console alternative, new default shortcut, persistent MRU, feature flag, rollback/off mode, terminal engine replacement, process multiplexing, same-session mirror, hidden-terminal eviction/suspension, automatic code split, general multi-project virtualization, changed remote lifetime, new bridge credentials, broad navigator redesign, or external URL-navigation feature. There is no promise of continuous visibility with code in the same editor group, memory/CPU savings, preserved terminal view state across IDE restart or actual cross-project console recreation, or proven usability improvement. This planning stage authorizes no source/test edits, builds, prototypes, IDE interactions, commits, pushes or delegation. Preserve the two untracked research deliverables and frozen Cairn trail unchanged.

## Chosen approach


### Presentation ownership and new responsibilities

Keep `AgentExecutionRegistry`, `AgentExecutionService`, `AgentExecution`, `OutputRouter` and `TerminalExecutionConsole` as process/console owners. Introduce the following types under the existing platform source root `intellij-plugin/src/platform/java/app/drydock/intellij/` (these names are proposed new symbols, not existing APIs):

- `agent/SessionHostController`: declarative project service and project-lifetime presentation authority. Owns primary/held session IDs, last intentionally activated session, previous session, last focused slot, request generations, retained session-pane map, and at most one live editor attachment lease. Publishes a new project-level `SessionHostListener` selection notification carrying an explicit `ManagedSessionId` when an actual intentional activation/focus changes the logical active session.
- `agent/SessionPane`: retained presentation for one immutable `(Project, ManagedSessionId)`. Extract the session strip, facts, body selection, stopped/dimmed input-blocking view and shared-command calls from `AgentConsoleEditor` into this responsibility, rather than copy its lifecycle policy. Its root contains that session's console component; switching outer slots moves/removes the **pane root**, not the process or output sink. Its session ID never mutates. Cached panes and their terminal view wrappers survive ordinary switching and closing the host document while the project lives.
- `agent/SessionHostFile` and `agent/SessionHostEditor`: canonical nonphysical virtual file and the single disposable FileEditor wrapper. Canonical URL is newly introduced `drydock-agent://sessions`, resolved by the existing registered filesystem independently of catalog readiness. File identity is stable and may be shared as an address across projects; **all mutable selection, hosted facts and Swing components are project-scoped**, never stored globally on that canonical file. The editor contains a host toolbar and primary plus optional held slots. Its title is `Drydock Sessions`; each pane independently names title, worktree/repository/branch, provider/RO/remote context and lifecycle status. The focused pane is visibly distinguished.
- `agent/SessionHostState`: separate project `PersistentStateComponent`, workspace-file storage using the existing `InboxViewState` pattern. Persist only the last intentionally shown session ID as cosmetic presentation state. Do not add this selection to core `ApplicationState` or create another writer for the shared catalog. No persisted previous/held IDs. Malformed stored ID decodes leniently to no selection.
- `agent/SessionHostMigration` and `agent/LegacySessionEditor`: one project reconciler plus inert compatibility editor. Old UUID files remain resolvable addresses, not a second live presentation. Legacy editors create no panes, consoles, timers, transcript probes or execution attachment. The old live `AgentConsoleEditor` responsibility is replaced/extracted, not kept as a selectable presentation mode.
- `tasks/AllSessionsAction`: registered Find Action entry, the Sessions toolbar's `All Sessions…` action, and a Drydock tool-window title action installed by `DrydockToolWindowFactory`. The latter uses verified `ToolWindow.setTitleActions(List<AnAction>)`, avoiding new navigation UI inside the oversized TaskTreePanel. A small `tasks/SessionActivation` responsibility shares stable-ID, intent-bearing explicit activation routing between the picker and existing inbox activation. These are new types; no new default keymap assignment.

Selection uses ID-map lookup and a bounded component swap; the retained consoles keep their existing process/output/terminal costs, plus one cached presentation per visited session and at most two mounted roots. Complete-picker catalog enumeration and async fact refresh are not the ordinary switch hot path; reuse a catalog ID index rather than repeated large-catalog scans. No allocation/latency saving is claimed.

These are component/interface boundaries, not a task/file ownership list. Split helpers further only without changing their contracts or introducing another authority. Keep new files under approximately 1,000 lines/50KB.

### Same-project switching and lifecycle

An intentional show resolves the named session in the appropriate project under existing facade/routing policy. A cold pane may immediately show a truthful loading placeholder/available known facts and schedule its necessary initial metadata work asynchronously; facts are not a synchronous prerequisite for console selection. Preserve existing off-EDT initial/catalog-change fact refresh semantics (including resumability/token/transcript discovery where necessary), with generation checks and honest failures. Repeat selection of an initialized pane reuses its facts and must not rescan transcripts or trigger a fresh metadata probe merely because it was selected again. If it is held, focus that existing pane and leave primary unchanged. Otherwise place its retained pane in primary, detaching the preceding pane root from the visible slot without disposing it. Reopening the host reattaches the existing layout and restores its last focused available pane; it never substitutes another session when the intended one is gone. Show, restore, previous return and migration never invoke Start/Resume or remote reattach. A stopped execution retained by the owning project stays readable through the existing dimmed/input-blocked stopped view; absent transcripts remain absent rather than replayed from disk on selection.

Ordinary switching of a console already owned by this project performs memory lookups and Swing layout/focus updates. It must not call registry `release`, `moveTo`, router `attach/detach`, project opening or process launch. The switch hot path never waits for metadata or scans transcripts; cold initial/catalog-change facts may be scheduled separately as above, not rescanned per switch. An execution newly started by an explicit lifecycle action still follows the existing registry creation path. Explicit Show Here/own-window moves remain distinct and can recreate consoles under existing guards. The controller responds to move/forget events by invalidating **only that session's pane/slot**, not closing the shared Sessions document or a different session. It leaves truthful moved/unavailable/no-selection presentation with no automatic replacement input target.

Document close detaches the editor attachment and hides both slots; it does not release/dispose the cached session panes or execution consoles. Project disposal stops presentation timers/listeners, invalidates queued work and disposes cached presentation wrappers; execution consoles remain children of `AgentExecutionService`, and current close/quit local/remote policies remain authoritative. There is no new background executor: metadata uses the owning plugin executor. Use one lifecycle-bound, coalesced presentation refresh/timer responsibility for the visible panes rather than retaining twenty independent editor tickers.

### Comparison and previous-session state transitions

`Hold current session` applies to a resolved primary pane only when secondary is empty. It moves A's existing pane root into secondary, clears primary, retains A as focused if focus was in A, and leaves an explicit primary empty-state with All Sessions access. It never invents B. The held pane can be stopped; merely holding it launches nothing. When secondary is occupied, Hold is disabled with an explanation to close the held view first. `Close held view` hides only secondary and clears that slot, preserving A's console/pane. If keyboard focus was in A, move it to the host's neutral toolbar/chooser, **not automatically to another agent**. A remaining primary continues to display its own identity. Closing the document preserves the two-slot layout only in memory. Across restart, the remembered last intentionally active session, even one formerly held, becomes primary; there is no restored held slot.

Maintain two in-memory IDs per project: current intentional session and previous distinct intentional session. Intentional session activation, explicit pane focus and previous return commit this pair; same-ID repeats do not push history. Picker highlight, inbox browsing, status/attention, catalog refresh, code-tab selection, restore, migration, Hold and close do not push it. Previous return swaps current/previous so repeated use toggles A/B; it focuses a held target in place, otherwise shows the target in primary. It is **presentation-only even for a stopped previous target**, unlike explicit stopped-row activation. Missing prior IDs remain unavailable with an explanation, not skipped to an arbitrary candidate. No new project open/move is caused by this local return: if a previously owned execution moved to another project, retain an honest detached/unavailable view and existing explicit Show/own-project actions. Previous is a real keyboard-accessible toolbar action and registered Find Action entry, with no default shortcut or persisted list.

### Complete navigation without rewriting the inbox

The All Sessions picker reads the complete catalog snapshot, not `InboxList.entries()` or the filtered/truncated inbox model. With no picker query it lists all catalog sessions across the catalog's existing project coverage, including Idle and sessions beyond row four. Show title, status/activation intent, worktree and stable-ID disambiguation; use full ID in details where a shortened ID could collide. A local picker search is independent of existing inbox title/project/status filters. Do not clear those filters, expand groups or conflate row highlight with committed host selection. Reachability includes browsing the unfiltered picker without knowing an exact title.

Running activation captures a Show/navigation intent and follows `TaskNavigator.switchTo`; if the execution ends while resolving, do not convert that captured intent into Start/Resume. Stopped Enter/double-click activation deliberately follows `AgentConsoles.resumeOrStart`, which preserves existing conversation/provider and launch guards. Show-versus-Start-or-Resume labeling is explicit; blocking resumability discovery stays asynchronous with progress. Re-resolve the captured stable ID at invocation, not row index after regrouping. A deleted ID fails honestly. Existing inbox multi-select, project/title/status filtering and group truncation remain intact. Replace TaskTreePanel's session-file-based selection subscription with the explicit project selection event, retaining its existing materialized-row-only selection behavior; the pane header and picker provide completeness when no matching row is materialized.

### Explicit command targeting, asynchronous facts and focus

Keep `SessionCommands` and `SessionCommandHandlers` as the policy/side-effect layers. Every pane button/menu binds immutable project, session ID and the painted lifecycle intent. For native editor-header/tab-popup commands, the canonical host file resolves to **that project's last focused attached pane**, not the globally selected editor or a session inferred from the canonical file. The native command label names the target. With no resolved target it is disabled/absent. Capture target identity plus selection generation on the actual painted header component/popup item; reject a stale click whose target/generation no longer matches instead of using a later pane's target. Apply this identity check to non-lifecycle destructive/navigation commands as well. Retain the current component-local painted lifecycle latch and fail-closed behavior: the SDK's header click clones the action template, so presentation user data alone is insufficient. Do not store per-project/session intent on globally shared AnAction instances.

Move file-local cached facts (`knownResumable`, checkout gone, hosted-from, token estimate) to the immutable pane's project/session facts. Adapt `AgentTabCommands`, `HostedTab` consumers, close-dialog hosted labels and own-project fallback to read those explicit facts, not a mutable singleton file's user data. Keep `AgentConsoleTabPresentation`'s local/detached/remote status derivation truthful when reused for pane/picker presentation; remote liveness is not local activity. No synchronous disk probing in action updates, titles or icons.

Background fact work returns immutable `(session ID, request generation, facts/failure)` results. EDT application verifies pane validity, project lifetime and newest generation before modifying that pane; an obsolete result cannot paint another slot or retarget commands. Catalog-loading, failed initialization, unknown ID and deleted ID are distinct honest states; unknown ID must not remain forever `Starting…` after initialization completes. Refresh callbacks do not request keyboard focus. UI open/focus requests also carry a project presentation epoch/target: newer explicit activation, code selection, hide/disposal or user focus departure invalidates older pending focus. The shared `AgentConsoles` facade fences `focusConsoleLater` and the existing README-grace callback against this current request permission; stale launch/transfer completion does not reopen a hidden host or take typing back from code/search/another session. Preserve launch progress cleanup and process outcomes even when presentation permission expires. Review/transfer launch policy is not changed merely to fence their existing focus callbacks.

### Visibility and attention

Keep `AgentConsoles.isBeingViewed(Project,id)` as the facade but require the session's **actual current console content** to be mounted and showing in its owning project's pane and the **actual ancestor window** to be active, not just a showing pane root, selected canonical file membership, ownership or a cached component. Resolve the owning project/current console through `AgentExecutionService.execution(id)`; the currently displayed console body and its component must match that execution, not an old retained component or a placeholder. Both visible real-console panes in the active ancestor window count as viewed under the named final-approval assumption, including an unfocused held console. Loading, detached, missing, unavailable and empty presentations never count: in particular previous return to a moved session must not acknowledge or suppress the elsewhere-owned live session's attention. Hidden retained consoles, code-replaced host and inactive windows do not count either; a detached editor window counts only when its actual real console is showing and that window is active. Use showing/selection/window-activation events to acknowledge only those viewed IDs. `AttentionNotifier` continues to coalesce/suppress/route explicit notification actions through its existing session and host destinations. Background attention changes update their indications and never select a pane, clear a filter or focus an agent. Explicit notification activation retains the named-session acknowledgement behavior.

### Canonical persistence, bounded compatibility and editor-instance limits

Preserve protocol `drydock-agent` and provider type ID `drydock-agent-console`; extend the existing DumbAware/HIDE_DEFAULT_EDITOR provider to handle canonical and legacy files. Resolve `sessions` without catalog checks; continue resolving syntactically valid UUID paths regardless of delayed catalog load; malformed paths remain unresolved. Do not normalize old UUIDs to the canonical file in VFS lookup: VFS has no Project argument and would discard the named address without a safe per-project selection channel.

Platform persistence remains the sole owner of whether an editor document is reopened. Drydock startup does not independently open remembered sessions. A newly introduced canonical address persists the one document; `SessionHostState` supplies only its selected ID. The project migrator responds to legacy editor creation/open notifications, coalesces reconciliation, opens/reuses the canonical document nonselectingly and without focus, then closes only inert old placeholders. This is conversion of restored addresses, not a competing startup session-restorer. It is idempotent and tolerates legacy events arriving in separate turns, delayed catalog initialization, duplicate UUID entries and catalog failure. No timer/event-order heuristic is used to guess which old ID was selected.

**First-upgrade limitation, authorized by coordinator:** passive legacy migration uses a remembered NEW-format selected ID or honest no-selection. It does not recover even a formerly selected legacy UUID from open order, selection events or the last restored address. This conservative limitation avoids unsupported restore-completion hooks and arbitrary input-target inference. Unknown/deleted remembered ID yields unavailable/no-selection, never another session. Later explicit application requests remain named: `AgentConsoles.show(project,id)` and existing facade callers pass the target directly to the controller and never open the old file. Unknown old URL editor events are treated as migration-only; there is no new general-purpose external legacy-URL navigation contract.

Use verified public target-SDK seams: `FileEditorManagerListener` open/close/selection callbacks; `FileEditorManager.requestOpenFile` with `FileEditorOpenRequest.defaults().withReuseOpen(true).withSelectAsCurrent(false).withRequestFocus(false).withUsePreviewTab(false)` for passive conversion; `FileEditorManagerEx.getWindows()/getCurrentWindow()/setCurrentWindow()/closeFile(file,window)` and `EditorWindow.getSelectedFile()/isFileOpen()/setSelectedComposite(file,false)` for narrowly scoped layout-preservation. No `FileEditorManagerImpl.initJob/waitInitialization`, internal `SINGLETON_EDITOR_IN_WINDOW`, raw workspace XML editing, reflection, new Kotlin/coroutine plumbing or guessed after-restore timeout. `FileEditorOpenRequest` is public Experimental in 263.7031.23; that version dependency is ASM-7, not falsely described as a cross-version stable API.

A nonselecting open alone is insufficient. At the EDT completion that will close placeholders, snapshot each surviving editor window's selected **nonlegacy** file, current editor window and relevant focus owner; close only the identified migration placeholders under a reentrancy guard; reselect still-open snapshotted code files in their same windows with `focusEditor=false`; restore the prior surviving current window and preserve an existing nonlegacy keyboard destination. Take this snapshot after the asynchronous canonical-open completion, not before waiting. Do not replay a stale selection snapshot over a later user action; check presentation epoch and file/window validity for delayed work. Selected legacy-only groups have no preserved code target and may disappear/land on the canonical no-selection host; never fill them with another session. Do not create arbitrary extra code splits to preserve empty legacy-only groups. Queued selection notifications from migration are not intentional activations and cannot update previous/remembered session IDs. Cancellation/failure/disposal clears the in-flight marker, logs/surfaces an honest error if the project survives, and never closes normal code documents. A retry is event/user driven, not an unbounded spin.

Set supported `FileEditorManagerKeys.FORBID_PREVIEW_TAB` and `FORBID_TAB_SPLIT` on the canonical file. Explicit opening reuses the existing editor wherever it is in this project; comparison is internal, not platform duplicate tabs. An attachment lease in the project controller prevents even a raced/restored duplicate FileEditor from mounting the Swing tree twice: the extra wrapper is inert and reconciled/closed by its exact editor-window identity without closing the legitimate host. Moving the single host to an allowed detached window remains one presentation, not a mirror. This bound is tested through actual platform split/duplicate/restore paths; a flag's presence alone is not proof. Normal code-tab stock actions remain unchanged.

### Settled readiness mechanism

The supervisor explicitly approved the following narrow internal decision in this run, including outside-lock callbacks and the test relocation below. Replace the deferred Executor facade with an **additional package-private loader constructor**:

```java
SessionFactsLoader(CompletableFuture<?> initialization, Executor pluginExecutor,
                   Probes probes, Consumer<Result> listener)
```

Retain the existing `SessionFactsLoader(Executor, Probes, Consumer<Result>)` constructor. Once readiness support exists, it delegates using successfully completed readiness. `Result`, `Probes.probe`, `select`, `refreshInitialized`, and `dispose` retain their existing package-private roles; no generic scheduler/cancellation interface is introduced.

The loader owns each request, not the executor or a discarded completion stage. Introduce a private request holder with immutable `(ManagedSessionId id, long generation)` and a monitor-protected terminal-result snapshot. The pending map identifies the current request for each ID. Install/capture requests under the loader's state monitor; release it **before** readiness registration, executor submission, or external listener invocation. A cache hit submits/registers nothing. An existing pending request is deduplicated and keeps its generation. A new request gets a monotonically increasing generation.

Register **non-async** `initialization.whenComplete` for that request, outside the monitor. Its callback performs only memory/state checks and these branches:

1. Inactive/disposed/superseded request: do nothing.
2. Exceptional readiness, including cancellation: construct an honest `FAILED` result directly from the supplied failure (nonempty message or exception-class fallback). Do not submit or run probes merely to discover/report that failure.
3. Successful readiness: call the supplied `pluginExecutor.execute` outside the monitor. Catch `RejectedExecutionException` from that call and complete the same request as `FAILED`. The submitted wrapper rechecks request validity before entering `load`/`Probes.probe`.

Only executor work calls blocking probes. A callback may run on the registering thread or readiness-completing thread; it never calls probes directly. “Executor work” is the execution boundary, **not** a promise that an executor can never use a previously used physical thread. Production supplies the existing non-inline plugin virtual-thread executor. Pure direct-executor tests may use only harmless in-memory probes; arbitrary inline executors are not production-safe for blocking probes.

All normal, probe-failure, readiness-failure and submission-rejection outcomes enter one loader-owned terminal-completion gate. Under the monitor it verifies non-disposal, current ID/generation/request and no previous terminal completion; records the request's terminal snapshot; clears that request's pending entry; and updates/removes cache exactly as below. Only an accepted terminal completion invokes `Consumer<Result>`, **once, outside the monitor**. A rejected/stale completion does not modify pending/cache/history or notify. An exception thrown by the external recipient is not a second scheduling failure and must not cause another notification.

`select` remains nonblocking: it captures/installs state, dispatches outside the monitor, then takes a memory-only snapshot. It returns cached facts, otherwise that request's terminal result if already available (in particular synchronous `FAILED`), otherwise `LOADING` with its ID/generation. A synchronous failure therefore has one listener notification and a matching return value; returning that value is not a second notification. A later failure is reported through the same constructor listener. There is no waiting for readiness or worker completion. Concurrently superseded return values/callbacks remain subject to recipient generation checks.

### Cache, refresh and disposal

Preserve nonfailure cache entries, including `UNKNOWN` and `DELETED`; repeated selection performs no probe. Track “was known” separately: never-seen missing ID resolves `UNKNOWN`; previously known then missing resolves `DELETED`. A terminal `FAILED` clears its own current cache/pending entry but does not erase “was known.” The next explicit `select` can retry. A transient submission rejection can recover on the same successfully completed readiness future; selecting again against the **same failed/cancelled readiness future** fails again, not a fictitious recovery. No automatic retry/backoff is added.

`refreshInitialized()` snapshots only currently cached IDs and installs their replacement requests under the monitor, then dispatches outside it. Cached answers remain readable until replacement terminal completion; pending-only IDs are not independently refreshed. A newer refresh supersedes the prior request. Its accepted failure removes the old answer; a stale failure cannot remove a newer answer. Refresh after disposal is a no-op.

`dispose()` invalidates/clears loader-owned pending/cache/known-history state. It neither cancels the **shared** plugin initialization future nor shuts down the plugin executor. Dispose returning before readiness settles prevents that request's subsequent submission and notification. Work accepted but not started checks validity before probing; work already past that check may finish, but its late terminal outcome is dropped. A dispose/supersede racing the check-to-submit interval may leave a queued no-op wrapper; do not claim atomic revocation of an external `execute` call. Post-dispose `select` retains the draft's inert generation-0/LOADING sentinel and schedules nothing; it is not a result to paint in a surviving pane, whose lifetime fence must reject disposed-loader callbacks.

Completion accepted before disposal/new generation can already have a listener invocation in flight outside the monitor. Do not claim to revoke it or hold the monitor while calling recipients. The existing project/pane lifetime plus ID/generation check on **EDT application** remains mandatory; callbacks can arrive on any thread and never focus a pane.

### Observable cancellation boundary

Supported cancellation is specifically `initialization.cancel(...)` / a cancellation exceptional outcome of the supplied readiness `CompletableFuture`, observed by `whenComplete`. Submission refusal is specifically an `execute` call throwing `RejectedExecutionException`. Probe exceptions retain the existing `Exception | LinkageError` failure mapping. These sources settle an active request through the gate even if no worker can be scheduled.

`Executor.execute` is void. An executor returning normally then silently discarding a Runnable, externally draining its queue, or suppressing execution without a cancellation/completion signal is **not observable through this seam**. No fictitious “cancel the executor's stage” test or guarantee is permitted: there is no exposed task stage/handle to cancel. With accepted queued work the request remains pending until that work runs, a supported failure occurs, or disposal invalidates it.
